# 0.3.0 加固计划（第二版）

> 对象：本仓库，基线 `v0.2.5` / `8df6fa9`
> 第一版经 codex 评审后大幅收敛。本版是**评审后**的范围，砍掉两项、改造两项、补两个边界。

## 评审结论与本版的取舍

| 项 | 第一版方案 | 本版决定 |
|---|---|---|
| 1 读路径 vs 写事务 | 手写共享读写锁 | **改**：统一互斥队列，砍掉读写锁 |
| 2 fsync | 手管 `open`/`sync`/`close` | **保留，简化**：`writeFile({ flush: true })` |
| 3 跨进程互斥 | `wx` 锁文件 + stale 接管 | **砍**：记录限制，不实现 |
| 4 `.tmp` 自动清理 | 按 mtime 保留最近 5 个 | **砍**：改为手工清理说明 |
| 5 写锁超时 | 排队超时 | **保留，补契约**：超时任务永久取消 |
| 6 锁作用域 | 未提及 | **新增**：同一存储文件跨 `apply` 共用队列 |
| 7 加载失败仍提交 | 未提及 | **新增**：读取失败时拒绝修改动作 |

**版本 0.3.0 合适，但发布说明不得宣称「五项全部解决」** —— 只有 1、2、5 修了，3、4 明确不修。

## 第 1 项：加载与写入的互斥边界

### 错误认知（第一版）

第一版以为危害只有「解析失败隔离可能搬走刚保存的新文件」，以为 `isolate: false` 就等于纯读。

**两点都错**：

1. **迁移也写盘**。`index.js:758` 处，旧版本 / 空内容 / `null` 文档会在加载时调
   `saveStore(document)`，整份覆盖正式文件。所以「加载」本身就可能是一个写事务，
   不能放在共享读锁里，也不该在锁外裸跑。
2. **读写锁换不到想要的收益**。共享读锁与独占写锁互斥，**写卡住照样堵 GET**；读写锁
   只允许读者之间并发。为一个拿不到的收益引入锁升级与公平调度，不划算。

### 方案

**所有会「加载并发布共享状态」的操作，进同一个互斥队列**：

```
统一队列 acquire(fn):
  - 已持锁的调用方使用内部变体 loadStoreInner()，不得重复 acquire（否则自锁死）
  - watcher / HTTP GET / bootstrap：acquire(loadStoreInner)
  - 工具入口：acquire(loadStoreInner → runAction)     ← 现状已如此
```

**迁移在独占事务内完成**：既然加载已经独占，迁移就自然安全，不需要额外设计。

**`saveStore` 不自行加锁**：它总是由持有事务的调用方调用，或由已独占的迁移调用。

**装配 hook 不进入磁盘锁**：它读的是已发布的内存快照，不该被 I/O 阻塞。

**保留「普通读取不主动隔离」**：读路径仍不做 `rename(storeFile, backup)`，因为隔离是破坏性
动作。但注意——读到坏内容时它仍会**修改 `state.document`**（退回空文档），这一点必须一起
处理，见下。

### 明确的代价（写进文档）

- GET 的重新读盘需要排队，可能因排队超时返回错误。这是本版接受的代价：优先正确性，
  而不是为一个拿不到的收益引入共享锁。
- 工具的 `list / preview / path / reload` 也走这个队列，因此同样可能排队超时。

### 共享状态倒退问题

即使禁止隔离和迁移，一次**延迟完成的旧读取**仍可能把 `state.document` 写回旧值。处理：

- 加载完成时**校验实例仍有效**（`registry(storeFile).state === state`），无效则丢弃结果、
  不发布。这与第 3 轮已经建立的 `adoptLegacyAgents` 守卫同一原则。
- 队列在**跨 `apply`** 层面共用（见第 6 项），所以新实例不会与旧实例各排一队。

### 测试

- **#22a** 坏 JSON 的普通读取**绝不** rename 文件（直接断言目录里没有 `corrupt-*` 新文件）。
- **#22b** 旧格式文档触发迁移时，迁移在独占事务内完成，且期间其他读取不会读到半成品。
- **#22c** 受控屏障复现「延迟的坏读取 + 一次成功保存」交错，断言正式文件仍是新内容。
- **#23** 改用单队列语义：断言所有加载/写入严格串行（用屏障记录进入/退出顺序），
  而不是第一版那个「两 GET 并发」的弱测试。

## 第 2 项：文件同步

### 方案

```js
await writeFile(tempFile, payload, { encoding: 'utf8', flush: true })
await commitTemp(tempFile, storeFile)
```

- Node 22.19+ 的 `writeFile` 支持 `flush`，负责写入后 sync 并关闭句柄，省掉自己管资源。
- **同步失败 → 不得 rename、不得发布新内存状态、不得删临时文件**（那份内容仍然是唯一的
  完整副本）。
- **rename 失败 → 保留完整临时文件**（维持现状）。
- Unix 上再尽力 sync 目录，**失败只记降级日志，不把已提交的保存伪装成没发生**。

### 表述修正（写进文档，不要说过头）

- 不是「Windows 无法打开目录」，而是**没有可依赖的、等价于 Unix 目录 fsync 的可移植保证**。
- 不说「保证文件内容落盘」，而说「请求刷新文件缓存，在操作系统/文件系统/存储设备支持的
  语义下提高持久性」。`FlushFileBuffers` 不只刷数据，也涉及文件元数据。
- **不写未经本机实测的性能承诺**（第一版那些「NVMe 亚毫秒」之类的数字删掉）。
- Node 的 rename 走 `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`，**没有** `MOVEFILE_WRITE_THROUGH`；
  该标志是原生 API 选项，标准 Node 不暴露。**不值得为此引入原生桥接**。

### 测试

- **#24a** 注入同步失败，断言：正式文件不变、内存状态不变、临时文件仍在。
- **#24b** 断言 sync 完成后才 rename（调用序列契约）。
- **诚实说明**：物理断电的持久性**无法**用单测证明。杀进程 ≠ 断电。本项只验证协议与
  故障分支，不宣称验证了持久性。

## 第 3 项：跨进程互斥 —— 本版不实现

### 为什么砍

第一版的 stale 接管方案至少有四条失效路径：

1. **活进程被误判 stale**。调试暂停、系统休眠、事件循环阻塞、慢盘都可能超 30 秒。
   超时不等于进程退出。
2. **迟到的接管者搬走新锁**。A、B 都读到旧锁；A rename 旧锁并建新锁；B 随后 rename
   原路径，搬走的是 A 的新锁。两次 rename 都成功，「失败者放弃」解决不了。
3. **旧持有者删除新锁**。原持有者恢复后无条件 `unlink(lockPath)`，删掉接管者的锁。
4. **空锁文件**。独占创建成功、写入时间戳前崩溃，留下空锁或半截锁，恢复规则未定义。

这是**互斥协议的正确性缺口**，不是靠「可关闭」和风险说明能补的。加身份令牌、心跳、
复查，也消不掉路径检查与删除之间的竞态。

**Windows 上「先 rename 再 unlink」绕不开共享删除限制**：`FILE_SHARE_DELETE` 同时管辖
删除与重命名，句柄不允许该共享时 rename 一样失败。

### 本版做什么

- **文档明确要求：一个存储文件只允许一个写入进程。**
- 在 README 的「限制」一节写清楚，并说明锁也约束不了直接编辑文件的外部程序。
- 将来有真实多进程需求时**单独设计**，不塞进这一版。

## 第 4 项：`.tmp` 累积 —— 本版不做自动清理

### 为什么砍

第一版「成功后按 mtime 保留最近 5 个」有两个问题：

1. **可能删除其他仍在执行的事务的临时文件**。mtime 和文件名都不能证明文件已废弃；
   一次暂停的事务，它的 tmp 完全可能掉出最新五个。
2. **只在成功后清理，限制不了「持续失败」时的累积** —— 而持续失败恰恰是累积的成因。

另外，首次恢复成功时可能需要扫描、stat、大量删除历史文件，**延长保存和持锁时间**。
「失败不影响结果」不等于「耗时不影响结果」。

### 本版做什么

- 保持「rename 失败时保留临时文件」不变（那是对的，它是唯一恢复材料）。
- **README 写手工清理方法**：文件形如 `<basename>.<pid>-<ts>-<nonce>.tmp`，
  确认内容无误后手工删除即可；只要不删正在写入的那个，没有风险。
- 不做活跃文件登记、不做后台清理生命周期 —— 那是为清空清单而增加的新故障面。

## 第 5 项：排队超时

### 方案

`acquire(fn, { waitMs = 10_000 })`：在 `waitMs` 内没轮到就 reject，错误码
`WRITE_QUEUE_TIMEOUT`。

### 实施要求（每一条都必须真的做到）

1. **超时后，任务即使以后轮到，也绝不执行**（不是提前返回错误、任务照跑）。
2. **任务一旦开始，停止排队计时**（已开始的任务不受 `waitMs` 约束）。
3. **不能因为超时提前释放实际仍被占用的锁**。
4. **成功、失败、超时都不能毒化队列**；计时器必须清理，不留悬挂 timer。
5. **503 必须落到 HTTP 层**：现在 `index.js:2104` 统一返回 500，不会自动变成 503。
6. **文档说明**：`list / preview / path / reload` 也走这个队列，同样可能排队超时。

**用 `Promise.race` 提前 reject 而让任务继续保存，正好制造「报失败但实际改了」——
这是本项唯一必须避免的错误实现。**

### 测试

- **#28a** 第一个任务永久 pending → 第二个在 `waitMs` 后 reject 且错误码正确。
- **#28b** **释放第一个后，断言第二个从未执行**（这是第一版漏掉的、也是最危险的那条）。
- **#28c** 第三个任务仍能成功（队列没被毒化）。
- **#28d** 已开始的任务超过 `waitMs` 仍保持独占，不被中途打断。

## 第 6 项（新增）：锁作用域必须跨 `apply`

### 问题

现在的队列是 `apply` 闭包里的 `writeChain`（`index.js:444`）。热重载意味着：

- **旧实例的在途操作不会因 disposer 执行而停止**，它们仍在跑。
- 新实例创建**新队列**，与旧队列互不知情。
- 加 fsync、等待、重试**会扩大**重叠窗口。

### 方案

队列和锁身份挂到 `globalThis` 的 registry entry（与 `agents` / `state` 同处），
跨 `apply` 共用同一个串行队列：

- **过期实例的排队任务不得再开始**（开始前校验实例有效）。
- **在途事务不能被强行解锁**，让它跑完。
- 事务完成后**不得重新接管 agent**（已有的守卫继续有效，但需覆盖加载 / 保存 / 刷新）。

### 测试

- **#29** 真 `reapply` 场景下，旧实例的在途事务与新实例的写不得交错；旧实例的排队任务
  在新实例接管后不再开始。

## 第 7 项（新增）：加载失败时拒绝修改

### 问题

工具入口拿到 `{ ok: false }` 后只跳过 agent 迁移，**照样执行 `runAction`**。
I/O 失败时可能拿旧内存覆盖当前磁盘；隔离失败时还可能覆盖未成功备份的坏文件。

### 方案

- **读取失败允许展示旧快照**（GET 只读展示，可以继续）。
- **修改动作拒绝提交**：`runAction` 在文档不可信时返回错误，不写盘。
- 需要区分「这个动作是只读还是修改」——现有 action 列表需要逐个归类。

### 测试

- **#30** 注入 I/O 失败 → `list` 仍返回旧快照，`add` / `toggle` 等修改动作被拒绝且磁盘不变。

## 实施顺序（按评审建议调整）

「写锁超时放第一项」的理由不成立：它管不到正在执行的挂起任务、锁外加载或死锁，
而且被测超时机制本身也可能失效。**测试兜底应来自测试框架，不是被测代码。**

1. **先建测试基建**：受控 I/O 屏障、有界测试超时、反向验证方法。
2. **第 1 项**：统一加载 / 迁移 / 写事务的互斥边界。
3. **第 6 项**：把队列提到跨 `apply`（与第 1 项同批，否则等于白做）。
4. **第 5 项**：在最终队列上增加排队超时。
5. **第 7 项**：加载失败拒绝修改。
6. **第 2 项**：文件同步。

每项独立提交、各自完成反向验证。

## 测试纪律（本版新增）

- 测试必须**驱动生产入口**，不要只测一个生产中没真正使用的锁助手。
- 用**可控屏障**制造交错，不要靠固定 `sleep` 猜时序。
- 每个测试都要**有界超时**，否则挂住看不出是死锁还是慢。
- 反向验证不能只看「撤掉一行会红」，要能说明**红在哪个行为上**。

## 明确不做的

- **跨进程互斥**（协议正确性补不齐，见第 3 项）。
- **`.tmp` 自动清理**（无法证明文件已废弃，见第 4 项）。
- **任务执行超时**（JS 无法抢占，强行超时会造成「报失败但实际改了」）。
- **读写锁 / 锁升级 / 公平调度**（收益拿不到，见第 1 项）。
- **`.corrupt-*` 自动清理、debug 日志轮转**：那是恢复证据和诊断材料，只写维护说明。
- **借机重构 hook 注册与清理机制**：那是前六轮刚修好的，不动。

`0.3.0`。可观察的行为变化：排队失败返回 503、加载失败时修改动作被拒、保存略慢。
发布说明准确列出「改善了 1/2/5/6/7，保留限制 3/4」。
