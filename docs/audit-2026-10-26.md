## 已知但未修（发版时记录）

| 项 | 依据 | 说明 |
|---|---|---|
| 读写竞态 | `loadStore` 的解析失败隔离、watcher / HTTP GET / bootstrap 未与写事务统一串行 | 延迟的坏 JSON 读取可在成功保存之后把新文件隔离。工具入口本身已在写锁内 |
| 无 fsync | `saveStore` 只有 `writeFile` + `rename` | 成功返回不代表断电后持久 |
| 无跨进程互斥 | 写队列是实例闭包 | 两个进程指向同一 storeFile 时可基于同一旧快照互相覆盖 |
| `.tmp` 累积 | rename 重试失败时保留临时文件 | 持续失败会累积 `N × 文档大小`。保留是刻意的：删掉等于销毁唯一恢复材料 |
| 写锁无超时 | `withWriteLock` | 前一任务一直 pending 时后续任务一直排队 |

## 处理

全部修复，commit `3b6ce18`。测试侧的关键改动是给 harness 加了 `reapply()` ——
真正再跑一次 `apply()`（换实例），这才是宿主热重载做的事；`reload` 只重读文件，
跨实例的 bug 用它一个都测不出来。

修复后已逐个反向验证：撤掉 `lastDocument` → #14 转红；撤掉 document 传递 → #17 转红。

## 已知但未修

- **读写竞态**：`loadStore`（watcher、HTTP GET、工具读取）都不在写锁内；解析失败隔离也没有与写事务串行化。仍可复现「延迟读取返回坏 JSON → 中间成功保存新文档 → 延迟读取把新文件隔离」。修复需要把读路径也纳入锁，改动面大于本轮。
- **写入没有 fsync**：`writeFile` 返回不代表断电后持久，无法对掉电做保证。
- **rename 连续失败会累积 `.tmp` 文件**：每次失败留一份完整文档，空间约 `N × 文档大小`。是保留策略问题（删掉等于销毁唯一的恢复材料），目前只记日志。
- **`withWriteLock` 没有超时**：一次卡住的写入会一直占着锁。
- **无跨进程互斥**：两个 DSH 进程指向同一个 storeFile 时没有仲裁。

## 未被采用的设计建议

- 「waterfall 更外层 listener 在回程中仍可继续修改，不能保证本插件是整条链的最终裁决」—— 成立，但这是流水线语义的固有性质；插件选择「先 next 后加工」已经是在不给下游添乱前提下的最强位置。
