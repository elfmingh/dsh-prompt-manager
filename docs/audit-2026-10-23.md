## 1. [P1] HTTP 接口缺少鉴权，可直接读取和修改所有提示词

位置：`index.js:1210`、`index.js:1222`、`index.js:1400`。

接口直接挂在 `webServer.register()`，GET 返回完整档案，POST 直接调用 `toolDefinition.execute()`；没有 cookie、令牌、来源或权限检查。宿主 `dsh-host-webserver/lib/index.js:384` 直接派发到路由，README 也明确说明没有统一的 authentication/origin policy。其他 Host RPC 的登录保护不能自动覆盖这条自定义路由。

复现结果（仅临时存储）：

```text
无认证 GET /prompt-manager/api
=> 200，返回 private-fixture 档案

无认证 POST /prompt-manager/api
Origin: https://untrusted.example
Content-Type: text/plain
{"action":"library.add","id":"unauthenticated-write","text":"test only"}
=> 200，已创建档案 unauthenticated-write，文件中存在该条目
```

影响：能连接监听地址的调用方可以读取提示词、临时条目与装配快照，持久化修改全局或指定会话的规则。监听非回环地址时可扩大到对应网络。接口同时接受外域来源的简单 POST；真实浏览器能否送达还取决于其本地网络访问限制。

建议：接入宿主实际的请求认证机制，对写操作校验来源/CSRF，并限制请求格式和体积；在校验通过前不得读写业务数据。只限制 CORS 响应头不足以阻止写入。

## 2. [P1] 并发写入均报告成功，却丢失已提交数据

位置：`index.js:354`、`index.js:831`、`index.js:853`。

每次修改先读取同一份 `state.document`，等待 `writeFile()` 完成才更新内存。并发操作会从同一个旧版本生成不同的完整文档，再互相覆盖。

复现：对两个 `library.add` 使用 `Promise.all()`，分别增加 `one` 和 `two`。

```text
返回：[已创建档案 one, 已创建档案 two]
落盘 entries：[two]
```

影响：多标签页、HTTP 和模型工具同时操作时可静默丢失档案、应用配置或规则。当前测试全部串行调用，未覆盖这个情形。

建议：将“读取最新状态—修改—保存”整个事务串行化；仅串行化最后的文件写入仍会提交旧版本。保存采用临时文件和原子替换，并协调 watcher/GET reload 与事务的顺序。

## 3. [P2] 后注入开关永远返回未知 action

位置：`index.js:798`、`index.js:932`；调用方 `client.js:635`。

入口将 action 转成小写，但分支仍比较混合大小写的 `apply.hotReload`，因此永远无法匹配。

```text
输入：{action:"apply.hotReload", workspacePath:"D:/work", enabled:true}
返回：error: 未知 action apply.hotreload
```

影响：UI 和模型工具均不能开启或关闭工作区后注入。建议统一 action 的规范形式，并加入实际开关的回归用例。

## 4. [P2] 父会话临时条目无法传递给子代理

位置：`index.js:475`、`index.js:478`。

作用域过滤通过后，仍要求临时条目的 `sessionId` 与子代理自身的 ID 完全一致，没有匹配父会话或祖先链。UI 添加临时条目总是填写当前主会话 ID，因此选择“仅子代理”的条目实际不会注入任何目标子代理；默认的“主代理 + 子代理”也只能到达主会话。

复现：为 `main` 增加 `agentScope:"subagent"` 的临时条目，再建立 `parentSession:"main"` 的 `child`。子代理装配结果只有原始三段，没有该临时条目。

建议：明确继承边界，按可信会话父链解析临时条目的可见范围，并测试直接子代理、多级子代理及无关会话隔离。现有“临时条目作用域”测试省略了 sessionId，未覆盖 UI 的实际路径。

## 5. [P2] 动态条目的 replace 规则保存成功但不生效

位置：`index.js:674`、`index.js:681`。

内置 sections 完成规则处理后才追加动态条目；追加阶段只处理 `disable`，没有应用 `replace`。

复现：增加临时条目 `dynamic`，再对 `prompt-manager:temporary:dynamic` 设置会话级 `replace`。

```text
规则文本：REPLACEMENT
实际装配：{"name":"prompt-manager:temporary:dynamic","text":"original dynamic"}
```

影响：临时条目和后注入工作区条目的覆盖被忽略；主页却会根据已保存规则显示“覆盖生效中”。建议动态条目追加前复用完整规则处理逻辑，保持快照原文和最终文本的语义明确。

## 6. [P2] 普通提示词中的双花括号会导致宿主渲染失败

位置：`index.js:557`、`index.js:678`；宿主 `dsh-system-prompt/lib/index.js:118`、`:158`。

工具承诺文本原样注入，但静态注册和动态追加都没有设置 `interpolate:false`。宿主默认将 `{{name}}` 解释为变量引用，未知或格式错误的引用会抛异常。

验证使用从本机宿主源码提取的实际插值函数，以及插件生成的静态和动态 section：

```text
输入文本：Keep the placeholder {{user_input}} literal.
静态条目：unknown prompt variable "{{user_input}}" in section "prompt-manager:template"
临时条目：unknown prompt variable "{{user_input}}" in section "prompt-manager:temporary:template-temp"
```

影响：常见的模板示例会使应用这些条目的会话无法正常构建提示词。建议默认按字面量注入；若要支持变量模板，应作为显式功能校验并提供清晰的失败反馈。覆盖文本也需检查相同的插值语义。

## 7. [P2] 删除任意档案会关闭其他工作区的后注入配置

位置：`index.js:865`、`index.js:866`。

`library.remove` 重建所有工作区配置时只复制 enabled、disabled、default，丢失 hotReload；再次规范化时缺失值被置为 false，只有 hotReload 的工作区还可能整个消失。

复现：手工在临时存储中设置工作区 `d:/work` 的 `hotReload:true`，其启用条目为 `b`，reload 后删除无关档案 `a`。

```text
删除前 hotReload：true
删除后 hotReload：false
```

该复现绕过第 3 项失效的开关，验证已有配置和修复开关后的独立问题。建议保留工作区其他字段，再清理目标 ID，并把 hotReload 纳入是否保留工作区的判断。

## 8. [P2] 全部恢复后重新启用，会复活已清除的旧规则

位置：`index.js:424`、`index.js:618`、`index.js:1091`。

`override.reset` 清空文件中的规则并关闭总开关，但没有清除运行中会话的 `sessionBaselines`。再次启用总开关，或设置任何新规则自动开启开关时，旧基线再次生效。

复现：先全局覆盖 identity 为 GLOBAL，建立会话，执行全局 reset，再开启总开关。

```text
reset 后装配：base identity
重新启用后装配：GLOBAL
磁盘全局 sections：{}
```

影响：“全部恢复/清除全部规则”的结果不持久，运行中会话可能在无意中恢复旧的禁用或覆盖。建议定义 reset 对冻结基线的清理语义，确保明确的全量恢复不会被内存中的旧版本撤销。

## 9. [P2] 快照脚本写入未被忽略的目录，且调用废弃接口

位置：`scripts/snapshot-sections.mjs:20`、`:36`；`.gitignore:13`。

脚本实际请求 `view=system`，然后把含提示词和环境上下文的 JSON/Markdown 写到 `docs/sections-*.{json,md}`。README 声称使用 `view=assembled` 并写入 `docs/snapshots/`，而 gitignore 也只忽略后一个目录。

验证：`git check-ignore docs/sections-audit-probe.json docs/snapshots/sections-audit-probe.json` 只匹配第二个路径；没有创建或提交任何真实快照。

影响：维护者按文档运行脚本再执行常规批量暂存时，可能提交本应排除的系统提示词和环境信息；输出本身还受废弃接口的装配缺失影响。建议同时修正请求视图、失败状态处理及输出目录。

## 10. [P2] 插件未释放路由与 watcher，热卸载后可能继续保留旧逻辑

位置：`index.js:718`、`index.js:1210`、`index.js:1459`。

插件丢弃 `webServer.register()` 返回的 disposer，也没有返回清理函数或通过 ctx.effect 管理 watcher/timer。核对本机宿主，register() 只是向路由 Map 写入并返回删除函数，不会自动把这条注册绑定到调用插件的生命周期。

影响：卸载或 HMR 后旧 HTTP handler 仍可能持有旧 state 并继续提供读写；重新 apply 注册同一路径时，宿主会报 duplicate exact route，插件捕获错误后继续运行，可能形成新工具配旧 HTTP 的状态分裂。未关闭的 watcher 也会继续响应文件修改。

建议：将路由 disposer、watcher.close()、timer、agent section 清理统一纳入插件生命周期，并对 unload/reload 做集成验证。此项为静态交叉确认，尚未执行真实热卸载复现。

## 修复优先级

1. 先处理接口认证与写事务，防止未经授权的修改和静默数据丢失。
2. 修复 action、继承、动态规则和字面量渲染，再覆盖实际 UI 生成的参数组合。
3. 修复 reset、删除配置、快照输出和卸载清理；在真实 DSH 中验证会话装配、重载及 UI 状态。

现有测试通过说明已覆盖路径稳定，不能证明这些遗漏路径正确。尤其缺少并发写入、HTTP POST 认证、带 sessionId 的子代理临时继承、后注入开关、动态 replace、双花括号渲染，以及 reset 后重新启用的测试。
